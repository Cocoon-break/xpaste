# ADR-001：桌面端技术选型

| 项目 | 内容 |
| --- | --- |
| 状态 | 提议（技术验证通过后改为“已采纳”） |
| 日期 | 2026-10-18 |
| 决策人 | 产品负责人、客户端负责人 |
| 关联文档 | [xPaste 功能规格说明](xPaste-功能规格说明.md)（待确认问题 Q10）、[交互原型](xpaste-prototype.html) |

## 背景

xPaste 需要同时支持 macOS 和 Windows。选型按以下三个目标排序取舍：

1. **安装包尽量小**
2. **运行性能尽量高**：唤起面板 ≤ 100 ms，空闲 CPU < 1%，常驻内存 ≤ 150 MB（规格说明 5.1）
3. **维护成本尽量低**：两个平台尽量共用一套代码，设计改动不需要做两遍

另外两个约束：

- 交互原型已经用 HTML/CSS/JS 实现，包括毛玻璃、复制频谱和十几种动效。能直接复用原型的方案，可以省掉大量界面开发和对齐设计的工作。
- 剪切板监听、敏感内容标记、模拟粘贴、浮动面板、毛玻璃等能力必须调用各平台的系统接口（规格说明第 6 章）。无论选哪种方案，这部分都要写平台相关代码。

## 决策

采用 **Tauri 2.x（当前稳定版 2.12）**：

| 层 | 选择 |
| --- | --- |
| 应用框架 | Tauri 2.x，使用系统自带的浏览器内核（macOS 为 WKWebView，Windows 为 WebView2） |
| 界面 | 原生 TypeScript + Vite，不引入 React、Vue 等前端框架 |
| 后端 | Rust |
| 存储 | SQLite（rusqlite，随程序打包） |
| 平台接口 | Rust 直接调用：macOS 用 `objc2` 系列库，Windows 用官方 `windows` 库 |
| 毛玻璃 | `window-vibrancy` 库 |
| macOS 浮动面板 | `tauri-nspanel` 社区插件，或自行封装 `NSPanel` |
| 官方插件 | 全局快捷键、托盘、开机启动、单实例 |

## 候选方案

数字是常见经验值，不是本项目的实测结果，需要通过技术验证确认（见“行动项”）。

### 方案 A：Tauri 2.x（采用）

| 维度 | 评估 |
| --- | --- |
| 安装包 | 约 3–10 MB |
| 运行时内存 | 约 50–120 MB（含浏览器内核进程） |
| 唤起速度 | 面板窗口预先创建、隐藏常驻，可做到 100 ms 以内 |
| 维护成本 | 低：一套界面 + 一套 Rust 后端 |
| 原型复用 | 直接复用原型的 HTML、CSS、动效 |

**优点**：体积只比原生多几 MB；界面一套代码；原型可以直接迁移；官方插件覆盖托盘、快捷键、开机启动等常规能力。

**缺点**：内存比原生高几十 MB；macOS 的浏览器内核版本跟随系统和 Safari 版本；团队需要掌握 Rust。

### 方案 B：双端原生（macOS 用 Swift + AppKit，Windows 用 C++/Win32 或 WinUI 3）

| 维度 | 评估 |
| --- | --- |
| 安装包 | 约 2–5 MB（WinUI 3 如果自带运行库，要几十 MB） |
| 运行时内存 | 约 20–40 MB |
| 唤起速度 | 最快 |
| 维护成本 | 高：两套界面、两套业务逻辑 |
| 原型复用 | 只能作为参考，界面要重写两遍 |

**优点**：体积、内存、速度都最好；系统能力调用最直接。

**缺点**：毛玻璃、复制频谱和所有动效要在 Core Animation 和 Windows Composition 上各实现一遍；以后每次改设计都要改两处，并保证两端一致。

### 方案 C：Electron

| 维度 | 评估 |
| --- | --- |
| 安装包 | 约 80–120 MB |
| 运行时内存 | 约 150–300 MB |
| 维护成本 | 低 |
| 原型复用 | 直接复用 |

**否决原因**：安装包大小和内存都明显不符合目标 1、2。

### 方案 D：Flutter 桌面

| 维度 | 评估 |
| --- | --- |
| 安装包 | 约 20–40 MB |
| 运行时内存 | 约 60–120 MB |
| 维护成本 | 中：界面要用 Dart 重写，系统能力仍需分平台写原生代码 |
| 原型复用 | 重写 |

**否决原因**：体积比 Tauri 大好几倍，还要重写界面，三个目标都不占优。

### 方案 E：Qt / Avalonia

| 维度 | 评估 |
| --- | --- |
| 安装包 | 约 30–60 MB |
| 维护成本 | 中偏高：界面用 C++ / C# 重写 |
| 原型复用 | 重写 |

**否决原因**：同方案 D。Qt 还需要额外评估 LGPL 授权的合规要求。

## Tauri 版本选择

| 版本 | 状态（截至 2026-10-18） | 结论 |
| --- | --- | --- |
| **2.x** | 当前主力稳定版。最新 2.12.4 发布于 2026-10-14，2026 年已发布 16 个 2.x 版本 | **采用**。官方插件和社区插件都基于 2.x，资料和问题解答最多 |
| 3.0 alpha | 2026 年 9 月中旬开始发布，10 月 14 日到 alpha.5；官方文档说明 API 在正式版前仍可能变化 | 不采用。在 alpha 上开发需要不断跟随 API 变化 |
| 1.x | 旧版本，新功能和插件生态已转到 2.x | 不采用 |

3.0 新增的 CEF 运行方式会把完整的 Chromium 打包进应用，与“安装包尽量小”冲突。即使以后升级到 3.0，也继续使用系统自带的浏览器内核。

## 取舍分析

- **A 和 B 是真正的取舍**：B 在体积和内存上最好，但维护成本大约是 A 的两倍，而且还要再实现一遍原型。A 用几 MB 体积和几十 MB 内存，换来了一套代码和原型的直接复用。
- **平台相关代码躲不开**：剪切板监听、敏感标记、模拟粘贴、浮动面板焦点处理，在 A 和 B 中都要分平台实现。A 把这部分集中在 Rust 层，界面层不区分平台。
- **性能风险可控**：常驻内存目标是 150 MB 以内，Tauri 的常见占用在这个范围内；唤起速度靠预先创建并隐藏窗口来保证。这两项都列入技术验证。

## 影响

**变得容易的**

- 原型的界面和动效可以直接迁移，设计改动只改一处。
- 安装、托盘、快捷键、开机启动、自动更新都有官方插件。

**变得困难的**

- macOS 浮动面板需要“浮在全屏应用之上、不抢走焦点、粘贴后焦点回到原应用”，这需要原生代码，是项目里技术难度最高的部分。
- 团队需要掌握 Rust 的基本开发和调试。
- 系统 Safari 版本较旧的 macOS 不支持 `@starting-style` 和视图过渡动画，只能降级为更少的动效（原型已经写好降级处理）。

**需要后续再评估的**

- Tauri 3.0 正式版发布并提供迁移指南后，评估是否升级。
- 如果技术验证中内存或唤起速度不达标，保留 Rust 核心（监听、存储、粘贴），只把界面层换成双端原生界面（转为方案 B 的变体），已写的核心代码不作废。

## 降低维护成本的约定

1. `Cargo.toml` 中写 `tauri = "2"`，用 `Cargo.lock` 锁定具体版本；定期升级 2.x 小版本。
2. Rust 工具链不低于 1.90（Tauri 2.12 的最低要求）。Tauri 的最低版本规则是“最新稳定版往前数 3 个版本”，升级 Tauri 前先确认一下。
3. 直接调用 Tauri API 的代码集中在少数模块；剪切板、存储、粘贴等核心逻辑不依赖 Tauri，方便以后升级或替换界面层。
4. 前端不引入框架；列表虚拟滚动、状态管理按需手写。确实出现框架能明显省事的场景时，另立 ADR。
