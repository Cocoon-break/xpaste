# xPaste 图片文字识别（OCR）实现方案

**版本：** v0.2　**状态：** 已实现（阶段 10）　**日期：** 2026-10-20
**依据回写：** 已并入功能规格说明 v0.1.12（M22）与实现设计 v0.13（5.1、5.3、5.7、6、8、9.8、10）。下文保留方案原貌，只把“已跳过（图片过大）”统一改为“已跳过”；实现与方案不同的地方见 §13。
**依据：** 功能规格说明 v0.1.11（M05 搜索、M08 预览、M15 设置、第 8 章“本期不做：图片文字识别”）、实现设计 v0.12
**目标阶段：** 阶段 10

## 1. 目标与边界

**目标**

1. 复制或截图进来的图片，能按图中出现的文字被搜索到（M05 匹配范围扩展）。
2. 识别全部在本机完成，不联网、不上传、不落到数据目录之外（沿用现有隐私约束：日志与事件不含内容）。
3. 不影响记录与唤起的性能指标（记录延迟 ≤ 200 ms、唤起 ≤ 150 ms）：识别在后台异步进行，失败或超时只影响该条能否按图中文字搜到。
4. 不增加安装包体积、不引入模型文件：使用操作系统自带的 OCR。

**不做**

- 不做翻译、不做版面还原、不做表格 / 公式识别。
- 不识别视频帧、不识别 PDF 等文件类型（只处理 `kind = image`）。
- 不提供“按识别文字高亮图片区域”；预览里只给出纯文本。
- 不做云端或第三方 OCR 引擎的接入点（YAGNI；未来若需要，平台层函数签名不变，只换实现）。

## 2. 平台能力

| 平台 | 接口 | 语言 | 依赖 | 备注 |
| --- | --- | --- | --- | --- |
| macOS 10.15+ | Vision `VNRecognizeTextRequest`（`recognitionLevel = accurate`，`usesLanguageCorrection = true`，`recognitionLanguages = ["zh-Hans","zh-Hant","en-US"]`） | 简繁中文、英文等系统内置 | `objc2-vision`（与现有 `objc2-*` 同一体系，新增一个 crate） | macOS 12 起中文识别质量可用；10.15–11 只保证英文，中文结果可能为空，按“无文字”处理 |
| Windows 10 1809+ | `Windows.Media.Ocr.OcrEngine`（`TryCreateFromUserProfileLanguages()`，失败再 `TryCreateFromLanguage("zh-Hans-CN")`、`"en-US"`） | 取决于系统已安装的 OCR 语言包 | `windows` crate 已有，加 `Media_Ocr`、`Graphics_Imaging`、`Storage_Streams` 特性 | 没有任何可用语言时引擎为 `null`：按“本机不支持”处理（见 §8） |

两端同名同签名（沿用平台层约定）：

```rust
/// 识别一张 PNG 的文字。返回按阅读顺序拼接的行；None 表示本机没有可用 OCR 引擎。
pub fn ocr_png(path: &Path, max_side_px: u32) -> Result<Option<OcrText>, OcrError>;

pub struct OcrText { pub text: String, pub confidence: f32 /* 0–1，各行均值 */ }
pub enum OcrError { Decode, Timeout, Engine(String) }
```

- 输入统一为数据目录里已经落盘的 `images/<id>.png`（store 写图后才排队，不再从剪切板读）。
- `max_side_px`：识别前把长边缩到此值以内（默认 2000），兼顾速度与小字可读。
- 阻塞式函数，由应用层的工作线程调用；平台层内部不开线程、不发事件（与 `video_meta` / `video_poster` 同一形状）。
- Windows 的 WinRT 异步调用在工作线程里同步等待（windows-future 0.3 中为 `.join()`，见 §13）。

## 3. 数据模型与迁移

`records` 表加两列（迁移 4，只追加）：

```sql
ALTER TABLE records ADD COLUMN ocr_text  TEXT;                       -- 识别结果原文（不小写，供预览显示）
ALTER TABLE records ADD COLUMN ocr_state INTEGER NOT NULL DEFAULT 0;  -- 0 待识别 1 已识别有文字 2 已识别无文字 3 失败 4 跳过 5 本机不支持
-- （实现没有这条 UPDATE：默认值 0 已让历史图片进回填，见 §13）
```

- `search_text` 仍是唯一搜索字段：识别成功后 `search_text = search_text || char(10) || lower(ocr_text)`（Rust 侧 `to_lowercase()` 再写入，与现有做法一致）。
- `ocr_state` 的含义进 `RecordDetail`（`ocrState`、`ocrText`），列表摘要 `RecordSummary` 不带识别文本（避免列表载荷膨胀），只带 `ocrState` 用于行内小图标（可选，见 §6）。
- 删除记录时两列随行删除；清空历史不额外处理。
- `Settings` 加 `ocr_enabled: bool`（默认 `true`）与 `ocr_backfill: bool`（默认 `true`），按设置字段清单同步 `changed_fields`、`types.ts`、默认值测试、`settings-form.ts`。

## 4. 处理流程

```
剪切板线程 ──写库、写 images/<id>.png──▶ records 入库（ocr_state = 0）──▶ 发现有 record-added 事件（不变）
                                             │
                                             └──▶ OcrQueue.push(id)
OCR 工作线程（1 条，低优先级）
  循环：取 id → 读设置（关闭则把状态置 4 跳过并继续）→ 检查图片仍存在、未删除
      → 限制：文件 > 20 MB 或长边 > 8000 px → 状态 4 跳过
      → ocr_png(path, 2000)，超时 10 s（线程内计时；实现为软超时，只记日志，见 §13）
      → 写库：ocr_text / ocr_state / search_text 追加（一个事务）
      → 复用现有 record-updated 事件发该条摘要（摘要只带 ocrState，不带文本；前端 updated 处理器原地合并）
```

- **队列**：内存 `VecDeque<i64>` + `Condvar`；新复制的图片插队到队首，回填的历史图片排在队尾（最近复制的优先）。重复 id 去重。
- **启动回填**：`ocr_backfill` 为真时，启动后延迟 30 s 再把 `ocr_state = 0` 的历史图片按 `copied_at DESC` 入队，每张之间至少间隔 500 ms（避免电池机器上启动即满负荷）。面板可见期间暂停回填，隐藏后继续（唤起性能优先）。
- **失败重试**：状态 3 的记录不自动重试；预览里提供“重新识别”（§6）。
- **锁纪律**：写库时短暂持 store 锁，事件在锁外发出（沿用现有约束）。
- **来源过滤**：被忽略的应用与敏感内容本来就不入库，因此不会进队列；不额外判断。

## 5. 搜索

- 不改 `search_ids`：识别文字已并入 `search_text`，子串匹配与分类叠加自然生效。
- 列表高亮只作用于标题（M05 规则 4 不变）；命中在图中文字时，行内元信息末尾追加一小段上下文 `…识别文字中含“关键词”…`（取匹配位置前后各 12 个字符，`esc()` 后写入），让用户知道为什么命中。这需要摘要里带命中片段：由后端 `search_ids` 扩展为 `search(q) -> [{id, snippet?}]`，只在命中源是 `ocr_text` 时返回片段。
- 无结果文案不变。

## 6. 界面

**预览（M08 图片）**

- 信息栏新增“文字”字段：`待识别` / `N 字` / `无文字` / `识别失败` / `已跳过` / `本机不支持`。
- 预览正文图片下方加可折叠区块“图中文字”：默认收起，展开后显示 `ocr_text`（等宽、可选中），右上角“复制文字”按钮（复制到剪切板但标记为自身写入，不产生新记录——复用现有“跳过自身写入”机制）与“重新识别”按钮（状态 3、4 时显示：前端分不出“图片过大”与“关闭识别”，后端做不了时不改状态）。
- 识别完成时若正在预览该条，信息栏字段原地更新，不重绘整张图（避免闪动）；动效按 M20：文字变化用现有数字切换的 120 ms 淡入即可，不加新动效。

**列表（M07）**

- 不加新列、不改行高。可选：图片行的缩略图右下角加 10 px “T” 角标表示已识别出文字（默认实现，减少动态效果不受影响）。若产品觉得噪音大可去掉。

**设置（M15）**

- 新行“识别图片中的文字”开关（默认开），小字：`在本机完成，不上传；识别结果只用于搜索和预览`。
- 子选项“为已有图片补识别”开关（默认开），小字：`后台低速进行，面板打开时暂停`。
- 本机不支持时（Windows 无语言包、macOS < 10.15）：开关可用但下方提示 `当前系统没有可用的文字识别语言，可在“设置 > 时间和语言 > 语言”中为中文添加“光学字符识别”`（Windows）；macOS 旧系统提示 `需要 macOS 10.15 或更高`。
- 右键菜单不加项。

**状态栏（M19）**：不变。

## 7. 隐私与资源

- 识别在本机进程内完成；`ocr_text` 与图片同目录，随记录删除、随“清空历史”清除。
- 日志只记 `ocr id=N state=K ms=T`，不记文字。
- CPU：单线程、低优先级（macOS `QOS_CLASS_UTILITY`，Windows `THREAD_PRIORITY_BELOW_NORMAL`），单张典型 1500 px 截图 0.3–1.5 s。
- 内存：识别时额外 1 张解码位图（≤ 2000 px 长边 ≈ 16 MB），用完即释。
- 电池：面板可见暂停回填；回填间隔 500 ms；不在低电量模式下回填（macOS `NSProcessInfo.isLowPowerModeEnabled`，Windows 省电模式 `SYSTEM_POWER_STATUS.SystemStatusFlag`）——这一条如嫌复杂可先不做，列为 P2。

## 8. 错误与降级

| 情况 | 处理 |
| --- | --- |
| 引擎不可用（Windows 无语言包 / 旧 macOS） | 启动时探测一次并缓存；所有图片置状态 5，设置页给出提示；不弹窗 |
| 解码失败（非 PNG、损坏） | 状态 3；预览显示“识别失败” |
| 超时 10 s | 实现：只记 warn 日志，慢但成功的结果照常记录（软超时，见 §13）；原方案为状态 3 |
| 图片过大 | 状态 4；预览显示“已跳过” |
| 识别结果为空或置信度均值 < 0.3 | 状态 2“无文字”，不写 `search_text` |
| 记录在识别期间被删除 | 丢弃结果 |
| 设置中途关闭 | 队列剩余项全部置 4；已识别文字保留（仍可搜）；重新打开后回填只处理状态 0 / 4 |

## 9. 性能目标

| 指标 | 目标 |
| --- | --- |
| 记录延迟（复制到入库事件） | 不变，≤ 200 ms；OCR 不在此路径上 |
| 唤起 | 不变；面板可见期间不占 CPU（回填暂停、进行中的那一张做完即停） |

## 11. 分阶段任务（供阶段 10 计划展开）

1. **核心**：迁移 4、`ocr_text / ocr_state`、`Settings.ocr_*`、`Store::set_ocr(id, state, text)`（事务内追加 `search_text`）、`search` 返回命中片段。
2. **平台层**：`ocr_png` macOS（Vision）与 Windows（WinRT），`ocr_available()` 探测；两端 clippy 通过。
3. **应用层**：`ocr.rs` 工作线程与队列、启动回填、面板可见暂停、识别完成后发 `record-updated`、设置变更联动。
4. **前端**：预览“文字”字段与“图中文字”区块、重新识别 / 复制文字、列表命中片段、设置两项开关与进度 / 不支持提示。
5. **文档与验收**：规格新增 M22、M05 / M08 / M15 回写、附录文案；实现设计 §5 / §8 / §9；验收记录。

预计 5 个任务，可分两条流并行：1 → 3 → 4 为一条，2 独立一条（平台层只依赖签名）。

**可能的后续**：若 `search_text` 变长后搜索超过 50 ms，把搜索改为 FTS5 外部内容表（`unicode61` 分词 + 子串回退），那是独立一阶段。

## 12. 待产品确认（已确认，均取本方案默认）

1. 默认开启识别与回填（本方案按“默认开”设计；代价是首次升级后的一段后台 CPU 占用）。
2. Windows 没有中文 OCR 语言包时：按本方案“提示引导添加，不自动安装、不弹窗”。
3. 列表缩略图的“T”角标要不要（本方案默认做，可删）。
4. 命中片段显示在行内元信息里（本方案）还是只在预览里显示。

## 13. 实现与本方案的不同（阶段 10 回写）

1. **超时为软标记**：超过 10 s 只记 `ocr id=N 超过 10 s`（warn），结果照常记录；不把超时记为状态 3。硬超时需要可中断的 Vision / WinRT 调用，本阶段不做。原因：macOS 每个进程第一次识别要加载模型，约 8 s（开发构建实测 12.9 s），按 10 s 硬超时会把首张图片误记为失败。
2. **置信度**：Windows `OcrLine` 不给置信度，固定为 1.0，所以 Windows 上“均值 < 0.3 → 无文字”不起作用，只看结果是否为空。macOS 取各行 `topCandidates(1)` 置信度的均值。
3. **macOS 固定 `VNRecognizeTextRequest` 修订版 2**（系统支持时）：本机 macOS 27 上默认的修订版 3 `accurate` 首次调用要 30–330 s、之后每次失败，独立 Swift 程序也能复现。修订版 2 覆盖简繁中英，冷启动约 8 s、之后约 55 ms。
4. **解码与缩放两端共用 `image` crate**（按内容识别格式），不走 CGImage 工具或 Windows `BitmapDecoder`；Windows 缩放上限另取 `OcrEngine::MaxImageDimension()`。
5. **复制的图片文件也识别**：没有 `images/<id>.png` 时取记录的第一个仍存在的文件；解不开的格式（如 HEIC）记为失败。§2 原写输入只有 `images/<id>.png`。
6. **迁移 4 只有两条 `ALTER TABLE`**，没有 `UPDATE`：`ocr_state` 默认 0 即待识别。
7. **状态 4 的文案为“已跳过”**：后端对“图片过大”和“关闭识别”都记 4，前端分不出原因；“重新识别”对 3、4 都显示。
8. **面板可见时只暂停回填**（与 §7 一致）；新复制的图片与“重新识别”照常识别，识别线程为低优先级，不影响唤起指标；进行中的那一张做完即停。终审前曾暂停全部新识别，验收时首次引导面板一直开着，新截图要等约 9 s 才开始识别，因此改回只暂停回填。
9. **回填范围**：状态 0、4，引擎可用时还有 5（换了系统或装了语言包之后）；状态 3 不自动回填。设置里打开开关时立即回填，不等 30 s；中途关掉“补识别”时剩余回填项不处理、保持原状。过大跳过的行重新回填时只读一次文件头，状态不变不写库、不发事件。
10. **列表命中片段放在元信息行最前**，格式 `识别文字中含“…片段…”`，关键词前最多保留 4 个字：放末尾时 900 px 下关键词常被省略号截掉。片段由后端取命中处前后各 12 个字符。
11. **预览**：“复制文字”“重新识别”在区块右上角、识别文字之前（长文字不用滚到底）；“文字”字段变化直接替换，不加 120 ms 淡入（信息栏本来就是整段替换）。“复制文字”新增后端命令 `copy_text_plain`（只写纯文本、标记为自身写入）。
12. **低电量模式下不回填**（§7 末条）没有做，留作 P2。
13. **再次复制同一张图片**（去重命中）也会入队，已识别的由工作线程按状态丢弃。
14. **Windows 按词拼行**：`OcrLine.Text()` 在中文的每个词之间也插空格（“季 度 预 算”），搜索“季度预算”会搜不到。改为取 `OcrLine.Words()`，相邻两字都是中日韩字符（汉字、假名、谚文、CJK 标点与全角符号）时直接相连，否则加一个空格（`winfmt::join_ocr_words`）。需要 Windows 实机确认。
15. **关闭识别成批改状态**：队列里仍待识别的一条 `UPDATE … RETURNING id` 置为“已跳过”（`Store::set_ocr_many`），不逐行读写；前端把一帧内的多条 `record-updated` 合并成一次重绘。引擎不可用时回填成批改为“本机不支持”也按 500 ms 间隔，不一次发出上千条事件。
